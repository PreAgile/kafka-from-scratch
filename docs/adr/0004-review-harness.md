# 0004. 리뷰 봇에게 답을 주지 못하게 막는다

상태: 확정 (2026-09-18)

## 맥락

이 저장소에 AI 리뷰 자동화를 붙이려고 보니 문제가 하나 있었습니다.

AI 리뷰 봇의 기본 행동은 "여기 이렇게 고치세요" 와 패치 제안입니다. 프로덕션 저장소에서는 그게 정확히 원하는 동작입니다. 그런데 이 저장소의 목적은 동작하는 코드가 아니라 **내 머릿속에 남는 이해** 입니다.

봇이 답을 주면 나는 붙여넣고, 코드는 좋아지고, 학습은 0 이 됩니다. 리뷰를 붙일수록 프로젝트의 목적에서 멀어지는 역설이 생깁니다.

## 결정

리뷰어를 두 종류의 행동만 하도록 제약합니다.

1. 어긋난 지점을 가리키기
2. 스스로 답을 찾게 만드는 질문하기

수정된 코드, 패치, 의사코드, 클래스와 메서드 시그니처 나열을 전부 금지합니다. 이 규칙을 `.github/review-prompts/` 와 `.claude/commands/` 의 모든 프롬프트에 동일하게 박습니다.

리뷰의 주 입력을 diff 가 아니라 **PR 본문의 백지 설명** 으로 둡니다. 코드를 보지 않고 쓴 자기 설명과 실제 코드의 괴리가 곧 자각하지 못한 잘못된 모델이기 때문입니다.

예외를 하나 둡니다. `/adversary` 는 반례를 재현하는 **테스트 작성** 까지 허용합니다. 반례가 진짜인지 확인하려면 재현이 필요하고, 테스트는 답이 아니라 문제의 정식화이기 때문입니다. 프로덕션 코드 수정은 여전히 금지입니다.

## 결과

얻는 것은 학습 무결성입니다. 리뷰를 아무리 많이 받아도 구현은 내가 합니다.

잃는 것은 속도입니다. 봇이 고쳐주면 5분이면 끝날 것을 몇 시간 붙들게 됩니다. 이 프로젝트에서는 그 몇 시간이 비용이 아니라 산출물입니다.

이 결정이 강제하는 것이 하나 더 있습니다. **PR 을 반드시 거쳐야 합니다.** `main` 에 직접 푸시하면 백지 설명을 안 쓰게 되고, 백지 설명이 없으면 이 하네스의 주 입력이 사라져서 전체가 무용지물이 됩니다. 그래서 브랜치 보호를 겁니다. 혼자 하는 저장소에 브랜치 보호를 거는 이유가 협업이 아니라 학습 절차 강제라는 점이 이 프로젝트의 특징입니다.

## 대안

**일반적인 리뷰 봇을 그대로 쓴다**
설정이 0 이고 코드 품질은 가장 빨리 올라갑니다. 학습 목적을 정면으로 훼손합니다.

**리뷰를 아예 붙이지 않는다**
학습 무결성은 완벽히 지켜집니다. 대신 혼자 하는 프로젝트의 최대 약점인 "내가 모르는 것을 모르는 상태" 가 그대로 남습니다. 리뷰를 붙이려는 애초의 이유가 사라집니다.

**리뷰는 다 받되 답이 담긴 코멘트를 안 읽는 것으로 자제한다**
사람의 자제력에 기대는 설계는 실패합니다. 특히 막혔을 때 답이 눈앞에 있으면 봅니다. 프롬프트로 생성 자체를 막는 쪽이 확실합니다.

## 후기 (2026-09-18)

리뷰어 구성을 처음에 Claude + CodeRabbit + Gemini 로 잡았다가 확인 후 바꿨습니다.

**Gemini Code Assist 는 뺐습니다.** GitHub 통합이 아직 Preview 이고 유효한 Google Cloud 결제 계정을 요구합니다. 개인 무료 등급의 PR 리뷰 할당량도 공식 문서에서 확인되지 않습니다. 저장소 하나 붙이자고 GCP 프로젝트와 결제 계정을 만드는 비용이 얻는 것보다 큽니다.

**세 번째 관점은 Codex 로 채웠습니다.** ChatGPT 개인 구독으로 되고 결제 계정을 새로 만들 필요가 없습니다. GitHub Actions 를 쓰지 않고 `chatgpt.com/codex/settings/code-review` 에서 저장소별로 켜는 방식이라 시크릿도 필요 없습니다.

여기서 중요한 발견이 하나 있었습니다. Codex 의 리뷰 규칙은 **저장소의 `AGENTS.md` 의 `## Code Review Rules` 섹션** 에서 읽습니다. 이 저장소의 핵심 제약인 수정안 생성 금지를 Codex 에게도 강제할 통로가 이미 있었던 것입니다. `@codex fix` 요청이 와도 수정안을 만들지 말라고 명시해 두었습니다.

그래서 리뷰어 셋이 규칙을 읽는 위치가 각각 다릅니다. Claude 는 워크플로가 주입하는 `.github/review-prompts/`, Codex 는 `AGENTS.md`, CodeRabbit 은 `.coderabbit.yaml` 입니다. 같은 제약을 세 곳에 따로 박아야 했고, 하나라도 빠지면 그 봇이 답을 주기 시작합니다. 새 리뷰어를 붙일 때 가장 먼저 확인할 것이 "이 봇에게 규칙을 어디로 주는가" 입니다.

로컬 `/second-opinion` 은 그대로 둡니다. PR 을 올리기 전 단계에서 쓰는 것이라 역할이 겹치지 않습니다.

**Claude 는 개인 구독으로 돕니다.** `claude setup-token` 으로 장기 토큰을 발급해 저장소 시크릿에 넣으면 API 키 없이 동작합니다. 대신 사용량이 개인 구독에서 차감되므로, `pull_request` 의 `synchronize` 트리거를 뺐습니다. 푸시할 때마다 리뷰가 돌면 로컬에서 쓸 몫이 줄어듭니다.

이 저장소에서는 그 제약이 오히려 맞습니다. 리뷰의 입력이 백지 설명인데, 설명을 안 고치고 코드만 푸시한 상태에서 리뷰를 또 받을 이유가 없습니다. 다시 받고 싶으면 `/review` 코멘트를 남기면 됩니다.

**구독 사용량이 두 군데서 빠지게 됐습니다.** Claude 리뷰는 Claude 구독, Codex 리뷰는 ChatGPT 구독에서 차감됩니다. 무료인 것은 CodeRabbit 하나뿐입니다. 그래서 자동 트리거를 최소로 줄였습니다. 리뷰를 습관적으로 여러 번 돌리면 정작 구현할 때 쓸 몫이 줄어듭니다.

**도구 제약은 허용 목록이 아니라 거부 목록으로 걸어야 했습니다.** 처음에 `--allowedTools` 로 읽기 도구만 허용했더니 액션이 코멘트를 게시하는 자기 도구까지 막혀서, 잡은 `success` 인데 PR 에 아무것도 남지 않았습니다. 로그의 `permission_denials_count: 9` 로만 알 수 있었습니다.

`--disallowedTools "Edit,Write,MultiEdit,NotebookEdit"` 로 바꿨습니다. 애초에 막고 싶었던 것은 읽기 외의 모든 행동이 아니라 **파일 수정** 이었으므로 의도에도 더 맞습니다. 이제 수정안 금지가 프롬프트와 도구 권한 두 층에서 강제됩니다. 프롬프트는 모델이 어길 수 있지만 도구 권한은 못 어깁니다.
