# 0004. 리뷰 봇에게 답을 주지 못하게 막는다

상태: 확정 (2026-09-18)

## 맥락

이 저장소에 AI 리뷰 자동화를 붙이려고 보니 문제가 하나 있었습니다.

AI 리뷰 봇의 기본 행동은 "여기 이렇게 고치세요" 와 패치 제안입니다. 프로덕션 저장소에서는 그게 정확히 원하는 동작입니다. 그런데 이 저장소의 목적은 동작하는 코드가 아니라 **내 머릿속에 남는 이해** 입니다.

봇이 답을 주면 나는 붙여넣고, 코드는 좋아지고, 학습은 0 이 됩니다. 리뷰를 붙일수록 프로젝트의 목적에서 멀어지는 역설이 생깁니다.

## 결정

리뷰어를 두 종류의 행동만 하도록 제약합니다.

1. 어긋난 지점을 가리키기
2. 스스로 답을 찾게 만드는 질문하기

수정된 코드, 패치, 의사코드, 클래스와 메서드 시그니처 나열을 전부 금지합니다. 이 규칙을 `.github/review-prompts/` 와 `.claude/commands/` 의 모든 프롬프트에 동일하게 박습니다.

리뷰의 주 입력을 diff 가 아니라 **PR 본문의 백지 설명** 으로 둡니다. 코드를 보지 않고 쓴 자기 설명과 실제 코드의 괴리가 곧 자각하지 못한 잘못된 모델이기 때문입니다.

예외를 하나 둡니다. `/adversary` 는 반례를 재현하는 **테스트 작성** 까지 허용합니다. 반례가 진짜인지 확인하려면 재현이 필요하고, 테스트는 답이 아니라 문제의 정식화이기 때문입니다. 프로덕션 코드 수정은 여전히 금지입니다.

## 결과

얻는 것은 학습 무결성입니다. 리뷰를 아무리 많이 받아도 구현은 내가 합니다.

잃는 것은 속도입니다. 봇이 고쳐주면 5분이면 끝날 것을 몇 시간 붙들게 됩니다. 이 프로젝트에서는 그 몇 시간이 비용이 아니라 산출물입니다.

이 결정이 강제하는 것이 하나 더 있습니다. **PR 을 반드시 거쳐야 합니다.** `main` 에 직접 푸시하면 백지 설명을 안 쓰게 되고, 백지 설명이 없으면 이 하네스의 주 입력이 사라져서 전체가 무용지물이 됩니다. 그래서 브랜치 보호를 겁니다. 혼자 하는 저장소에 브랜치 보호를 거는 이유가 협업이 아니라 학습 절차 강제라는 점이 이 프로젝트의 특징입니다.

## 대안

**일반적인 리뷰 봇을 그대로 쓴다**
설정이 0 이고 코드 품질은 가장 빨리 올라갑니다. 학습 목적을 정면으로 훼손합니다.

**리뷰를 아예 붙이지 않는다**
학습 무결성은 완벽히 지켜집니다. 대신 혼자 하는 프로젝트의 최대 약점인 "내가 모르는 것을 모르는 상태" 가 그대로 남습니다. 리뷰를 붙이려는 애초의 이유가 사라집니다.

**리뷰는 다 받되 답이 담긴 코멘트를 안 읽는 것으로 자제한다**
사람의 자제력에 기대는 설계는 실패합니다. 특히 막혔을 때 답이 눈앞에 있으면 봅니다. 프롬프트로 생성 자체를 막는 쪽이 확실합니다.
