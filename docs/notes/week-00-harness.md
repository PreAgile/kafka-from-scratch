# 0주차: 리뷰 하네스를 세우며 배운 것

구현을 시작하기 전 주차입니다. 원본 분석과 리뷰 하네스 구축만 했습니다.

## 백지에서 설명할 수 있게 된 것

원본 구현의 결함 열두 가지와 실제 버그 네 개를 코드 위치까지 짚어 설명할 수 있습니다. 그중 A 등급 다섯 개가 Level 1~3 의 뼈대입니다.

특히 하나의 인과 사슬을 말로 풀 수 있게 됐습니다. Kafka 가 기본적으로 fsync 를 하지 않기로 했기 때문에 내구성 책임이 복제로 넘어가고, 복제가 책임을 지려면 몇 개가 받았는지 세야 해서 ISR 이 필요하고, ISR 이 생기면 아직 전체가 못 받은 구간이 생겨서 High Watermark 로 숨겨야 하고, 프로듀서가 어디까지 기다릴지 고를 수 있어야 해서 acks 가 존재합니다. 네 개가 따로 있는 기능이 아니라 하나의 결정에서 뻗어 나온 것입니다.

## 막힌 지점과 원인

Claude 리뷰가 PR 에 코멘트를 남기지 않는 문제로 시간을 많이 썼습니다. 원인이 세 개가 겹쳐 있었습니다.

1. `--allowedTools` 허용 목록이 코멘트 게시 도구를 제외했습니다. 거부 9건
2. 거부 목록으로 바꿨는데도 안 됐습니다. `track_progress` 가 꺼져 있어서 코멘트용 MCP 도구가 애초에 없었습니다. 거부 15건
3. `track_progress` 를 켜니 5초 만에 스킵했습니다. 워크플로를 고친 PR 에서는 액션이 자체 검증으로 건너뜁니다

**세 번 다 워크플로는 success 였습니다.** 이게 이 주차의 가장 큰 교훈입니다. CI 가 초록이라는 것은 산출물이 나왔다는 뜻이 아닙니다. 권한 거부도, 액션의 자체 스킵도 잡을 실패시키지 않습니다.

Level 1 부터 만들 로그 엔진에 그대로 적용되는 교훈이기도 합니다. `append()` 가 예외를 던지지 않았다는 것이 데이터가 디스크에 갔다는 뜻이 아닙니다. 원본이 정확히 그 함정에 빠져 있습니다. 복제를 던져놓고 결과를 보지 않은 채 클라이언트에 성공을 돌려줍니다.
