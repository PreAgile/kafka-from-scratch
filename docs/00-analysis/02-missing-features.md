# 원본에 없는 것들: 이것이 커리큘럼이다

`reference/` 코드를 읽으며 확인한 결함과 누락입니다. 각 항목은 "무엇이 없는가"로 끝나지 않고 **"그래서 어떤 장애가 나는가"와 "진짜 Kafka는 이걸 어떻게 풀었는가"**까지 적었습니다. 이 목록이 그대로 이슈가 됩니다.

우선순위는 A(치명), B(중요), C(성능/확장)입니다.

---

## A-1. 메시지 프레이밍이 없다

**증거**: `Protocol.encodeProduceRequest()` (reference/com/simplekafka/broker/Protocol.java:46)는 요청을 `[타입 1바이트][본문...]`으로 만듭니다. 전체 길이를 앞에 붙이지 않습니다. 브로커 `handleClient()` (SimpleKafkaBroker.java:519)는 1KB 버퍼로 `read()`를 한 번 호출하고 읽힌 것을 그대로 파싱합니다.

**무슨 일이 일어나는가**

TCP는 스트림입니다. 메시지 경계를 보존하지 않습니다. 따라서 세 가지가 전부 깨집니다.

1. 요청이 두 세그먼트로 쪼개져 도착하면, 첫 read에서 불완전한 바이트를 파싱하다가 `BufferUnderflowException`이 납니다.
2. 클라이언트가 요청 두 개를 연달아 보내 한 번의 read에 같이 들어오면, 두 번째 요청은 조용히 버려집니다. 파싱 후 남은 바이트를 아무도 보지 않습니다.
3. 메시지가 약 1KB를 넘으면 잘립니다. 버퍼가 1024바이트 고정입니다.

3번이 특히 악질입니다. 예외도 안 나고 에러 응답도 안 갑니다. payload 뒷부분이 사라진 채 로그에 기록됩니다.

**Kafka의 답**: 모든 요청과 응답 앞에 4바이트 크기 필드를 둡니다. 수신 측은 "4바이트 읽어 길이 N 확인 → N바이트가 다 모일 때까지 누적 → 그때 파싱"이라는 상태 기계를 돌립니다.

**진단으로 연결되는 지점**: 운영 중 "간헐적으로 메시지가 깨져서 들어온다"는 증상은 거의 항상 프레이밍이나 버퍼 재사용 문제입니다. 부하가 올라가야 재현된다는 특징이 있습니다. 작은 메시지, 낮은 부하에서는 요청 하나가 한 세그먼트에 들어가서 잘 동작하기 때문입니다.

## A-2. 복제가 fire-and-forget이라 acks=all이 존재하지 않는다

**증거**: `handleProduceRequest()`에서 `replicateToFollowers()`를 호출한 뒤 **결과를 기다리지 않고** 바로 클라이언트에 offset 응답을 씁니다. `replicateToFollowers()` 내부는 팔로워마다 `executor.submit()`으로 작업을 던지고, 받은 ack는 로그만 남깁니다.

**무슨 일이 일어나는가**

리더가 append 직후 죽으면, 팔로워에 아직 안 갔을 수도 있는 메시지에 대해 클라이언트는 이미 성공 응답을 받았습니다. 데이터 유실이고, 클라이언트는 유실 사실을 알 방법이 없습니다.

**Kafka의 답**: `acks` 설정으로 프로듀서가 내구성 수준을 고릅니다. `acks=all`이면 리더는 ISR의 모든 복제본이 해당 offset까지 따라온 뒤에 응답합니다. 여기에 `min.insync.replicas`가 붙어서, ISR이 너무 줄어들면 아예 쓰기를 거부합니다.

**함정 하나**: `acks=all`만으로는 부족합니다. `min.insync.replicas=1`이면 ISR이 리더 혼자 남았을 때도 "모든 ISR이 받았다"가 성립해서 그냥 `acks=1`과 같아집니다. 이 조합이 실제 운영에서 데이터 유실의 단골 원인입니다.

## A-3. ISR과 High Watermark가 없다

**증거**: `Partition`에 `leader`, `followers`는 있지만 ISR 개념도, 팔로워가 어디까지 따라왔는지를 추적하는 필드도 없습니다. `readMessages()`는 로그 끝(LEO)까지 무조건 읽어줍니다.

**무슨 일이 일어나는가**

복제되지 않은 메시지를 컨슈머가 읽습니다. 그 직후 리더가 죽고 다른 브로커가 리더가 되면, 컨슈머는 **존재하지 않게 된 메시지를 이미 처리해 버린 상태**가 됩니다. 컨슈머 관점에서는 데이터가 시간을 거슬러 사라진 것처럼 보입니다.

**Kafka의 답**: High Watermark를 둡니다. HW는 "ISR 전체가 따라온 offset"이고, 컨슈머에게는 HW 미만만 노출합니다. 아직 복제 안 된 구간은 존재하되 보이지 않습니다.

**연결**: HW는 A-2의 `acks=all`과 한 몸입니다. `acks=all` 응답 시점과 HW 전진 시점이 같은 조건에서 결정됩니다. 둘을 따로 배우면 안 되는 이유입니다.

## A-4. 리더 에포크가 없어서 커밋된 데이터가 사라질 수 있다

**증거**: `rebalancePartitions()` (SimpleKafkaBroker.java:431)는 리더가 없거나 죽었을 때 `brokers.get(0)`, 즉 **살아 있는 브로커 목록의 첫 번째**를 새 리더로 지정합니다 (SimpleKafkaBroker.java:448). 그 브로커가 해당 파티션의 복제본이었는지, 로그를 어디까지 갖고 있는지는 전혀 보지 않습니다.

**무슨 일이 일어나는가**

두 가지 시나리오가 있습니다.

1. **무자격 리더**: 그 파티션 데이터를 한 바이트도 안 가진 브로커가 리더가 되어 offset 0부터 다시 씁니다. 기존 데이터 전부 유실입니다.
2. **스플릿 브레인**: 옛 리더가 네트워크 분단 때문에 ZooKeeper 세션만 끊겼고 프로세스는 살아 있다면, 자기가 아직 리더인 줄 알고 계속 append를 받습니다. 분단이 복구되면 두 개의 서로 다른 로그가 같은 offset에 다른 데이터를 갖게 됩니다.

2번이 무서운 이유는 **어느 쪽이 맞는지 offset만으로는 판별할 수 없기 때문**입니다.

**Kafka의 답**: 리더 에포크를 둡니다. 리더가 바뀔 때마다 단조 증가하는 번호를 붙이고, 각 레코드가 어느 에포크에서 쓰였는지 기록합니다. 팔로워가 새 리더에 붙을 때 "내 마지막 에포크는 E, 그 에포크의 끝 offset은 얼마냐"를 물어보고, 답보다 자기가 더 많이 갖고 있으면 그만큼 잘라냅니다(truncation).

**이 프로젝트에서 가장 중요한 항목입니다.** 에포크 없이 유실이 재현되는 시드를 시뮬레이터로 찾아내고, 에포크를 넣어 그 시드가 통과하는 것까지 보는 것이 Level 3의 목표입니다.

## A-5. CRC와 크래시 복구가 없다

**증거**: `Partition.append()`는 `[길이][payload]`만 씁니다. 체크섬이 없습니다. `initialize()`는 기존 세그먼트를 열 때 `countMessagesInSegment()`로 레코드 수만 세고, 마지막 레코드가 온전한지 검사하지 않습니다.

**무슨 일이 일어나는가**

길이 필드는 썼는데 payload를 쓰다가 프로세스가 죽으면, 다음 기동 시 그 길이만큼 읽으려다 파일 끝에 부딪히거나, 더 나쁘게는 **다음에 append된 데이터를 이전 메시지의 payload로 읽습니다.** 조용한 데이터 오염입니다.

**Kafka의 답**: 레코드마다 CRC32를 두고, 기동 시 마지막 세그먼트를 스캔해 CRC가 안 맞는 지점부터 잘라냅니다(truncate). 로그 끝에서만 손상이 발생한다는 가정이 append-only 구조 덕분에 성립합니다.

**설계상의 아름다움 하나**: append-only이기 때문에 "손상은 항상 끝에서만 난다"가 보장되고, 그래서 복구가 "끝을 자른다"로 끝납니다. 중간을 수정하는 파일 포맷이었다면 복구가 훨씬 어려웠을 것입니다.

## B-1. 메시지마다 fsync를 두 번 한다

**증거**: `Partition.append()`가 로그 채널에 `force(true)` (Partition.java:199), 인덱스 채널에도 `force(true)` (Partition.java:239)를 호출합니다. 메시지 한 건당 디스크 동기화 2회입니다.

**무슨 일이 일어나는가**

처리량이 디스크 fsync 지연에 직접 묶입니다. 안전하지만 느립니다.

**Kafka의 답**: 기본적으로 fsync를 **하지 않습니다**. OS 페이지 캐시에 맡기고, 내구성 책임을 복제로 넘깁니다. "디스크 N개에 동시에 안 내려도, 서버 N대의 메모리에 있으면 충분하다"는 판단입니다.

**이 판단의 인과 사슬이 핵심입니다.** fsync를 포기했기 때문에 복제가 필수가 되고, 복제가 필수이기 때문에 ISR과 HW가 필요해지고, 그래서 `acks` 설정이 존재합니다. Kafka 설계 전체가 이 한 결정에서 뻗어 나옵니다. ADR 0001에서 다룹니다.

## B-2. 인덱스가 조밀하다

**증거**: `updateIndex()`가 모든 append마다 16바이트 엔트리를 씁니다.

**무슨 일이 일어나는가**

메시지 하나당 인덱스 16바이트입니다. 평균 메시지가 100바이트라면 인덱스가 로그의 16%를 차지합니다. 인덱스 파일이 커지면 메모리 매핑 이점이 줄고, fsync 비용도 추가됩니다.

**Kafka의 답**: sparse index. 일정 바이트마다 한 번씩만 엔트리를 씁니다. 조회 시 인덱스로 근처까지 점프한 뒤 거기서부터 순차 스캔합니다. **정확한 위치를 찾는 인덱스가 아니라 스캔 시작점을 좁히는 인덱스**라는 발상 전환입니다.

트레이드오프가 명확합니다. 인덱스 밀도를 낮추면 공간과 쓰기 비용이 줄고 조회 시 스캔 거리가 늘어납니다. Level 1에서 밀도를 파라미터로 만들고 직접 측정합니다.

## B-3. 배치가 없다

**증거**: 프로듀서는 `send()` 한 번에 메시지 하나를 보냅니다. 요청 하나에 레코드 하나입니다.

**무슨 일이 일어나는가**

메시지 한 건마다 TCP 왕복, 요청 파싱, append, fsync가 발생합니다. Kafka의 성능이 나오는 이유의 대부분이 여기서 사라집니다.

**Kafka의 답**: RecordBatch. 프로듀서가 `linger.ms` 동안 모아서 한 번에 보내고, 브로커는 배치를 통째로 로그에 씁니다. 압축도 배치 단위로 합니다. 배치 안에서 offset은 델타로 저장해 공간을 줄입니다.

**진단으로 연결되는 지점**: `linger.ms`를 올리면 처리량이 오르고 지연이 늘어납니다. 이 곡선을 직접 그려봐야 "Kafka가 느려요"라는 신고에 어디를 볼지 알 수 있습니다.

## B-4. 컨슈머 그룹과 offset 커밋이 없다

**증거**: `SimpleKafkaConsumer`는 생성자에서 파티션을 고정으로 받고, offset을 메모리에만 들고 있습니다. 재시작하면 처음 준 값으로 돌아갑니다.

**Kafka의 답**: 그룹 코디네이터가 그룹 멤버십을 관리하고 파티션을 할당합니다. 커밋된 offset은 `__consumer_offsets`라는 **내부 토픽**에 저장합니다. 메타데이터를 자기 자신의 로그 시스템에 저장하는 재귀 구조입니다.

**운영에서의 의미**: 리밸런싱은 운영 장애 신고 1순위입니다. 멤버 하나가 느리면 전체 그룹이 멈추는 stop-the-world 리밸런싱이 원래 동작이었고, 이걸 줄이려고 incremental cooperative rebalancing이 나왔습니다. 이 프로젝트에서는 구현하지 않고 문서로만 다룹니다(ADR 0002 참조).

## C-1. 네트워크 계층이 스레드 낭비 구조다

**증거**: `acceptConnections()`는 accept 루프에서 `Thread.sleep(100)` (SimpleKafkaBroker.java:507), `handleClient()`는 read 루프에서 `Thread.sleep(50)` (SimpleKafkaBroker.java:537)을 돕니다. 채널은 non-blocking으로 설정해 놓고 Selector는 쓰지 않습니다.

**무슨 일이 일어나는가**

1. 연결당 스레드 하나를 점유합니다. 연결 수가 곧 스레드 수입니다.
2. non-blocking 채널에 블로킹 스타일 루프를 돌리니 데이터가 없으면 즉시 0을 반환하고, 그래서 CPU 스핀을 막으려고 sleep을 넣었습니다. **지연의 하한이 50ms로 고정됩니다.**
3. 복제할 때마다 팔로워에 새 TCP 연결을 엽니다. 연결 재사용이 없습니다.

non-blocking 채널 + sleep 루프는 blocking I/O와 non-blocking I/O의 단점만 합친 조합입니다.

**Kafka의 답**: Selector 기반 이벤트 루프(acceptor 1개 + network thread N개)에 요청 큐와 I/O thread 풀을 붙입니다. 브로커 간 연결은 유지하고 재사용합니다.

---

## C-2. zero-copy가 없다

`readMessages()`는 파일에서 JVM 힙으로 읽고, 다시 소켓 버퍼로 복사합니다. Kafka는 `FileChannel.transferTo()`로 커널 안에서 파일에서 소켓으로 바로 보냅니다. 페이로드가 사용자 공간에 올라오지 않습니다.

이게 가능한 이유는 **브로커가 메시지 내용을 해석하지 않기 때문**입니다. 그냥 바이트 묶음입니다. "브로커를 멍청하게 만든다"는 설계 선택이 커널 최적화를 가능하게 한 사례입니다.

## 그 외 실제 버그

읽으면서 발견한, 설계가 아니라 그냥 버그인 것들입니다.

| 위치 | 내용 |
|---|---|
| SimpleKafkaBroker.java:660 | `forwardProduceToLeader()`가 버퍼를 `9 + topic + message`로 잡고 실제로는 `11 + topic + message`를 씁니다. 리더가 아닌 브로커로 produce가 들어오면 `BufferOverflowException`이 납니다. 같은 요청을 만드는 `Protocol.encodeProduceRequest()`는 11로 제대로 잡고 있습니다 |
| Protocol.java 전반 | 버퍼 크기 계산에 `topic.length()`(문자 수)를 쓰고 실제로는 `topic.getBytes()`(바이트 수)를 씁니다. 한글 토픽명이면 버퍼가 터집니다 |
| SimpleKafkaBroker.java:355 | `electController()`가 `/controller` 노드를 `exists` 확인 후 생성합니다. 확인과 생성 사이에 다른 브로커가 끼어들 수 있습니다. ephemeral 생성의 원자성을 쓰면서 앞에 굳이 비원자적 검사를 붙여 놓았습니다 |
| Protocol.java:34 | `sendErrorResponse()`가 `channel.write()` 반환값을 확인하지 않습니다. 부분 쓰기가 나면 에러 메시지가 잘립니다 |

## 이 목록을 어떻게 쓸 것인가

A 항목 다섯 개가 Level 1~3의 뼈대입니다. 각각에 대해 이 순서를 지킵니다.

1. **결함을 재현하는 테스트를 먼저 씁니다.** 실패하는 걸 눈으로 봅니다.
2. 고칩니다.
3. 무엇을 포기했는지 ADR에 씁니다.

1번을 건너뛰면 이 프로젝트는 그냥 코드 옮겨 적기가 됩니다. 재현이 학습의 본체입니다.
