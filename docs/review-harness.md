# 리뷰 하네스: 피드백을 자동으로 받는 구조

이 프로젝트에서 리뷰는 코드 품질을 지키려고 하는 것이 아닙니다. **내가 뭘 모르는지 모르는 부분을 찾아내려고** 합니다. 그래서 일반적인 리뷰 자동화와 설정이 다릅니다.

## 설계 원칙 하나: 리뷰어는 답을 주면 안 된다

이게 이 하네스에서 가장 중요한 제약입니다.

AI 리뷰 봇의 기본 행동은 "여기 이렇게 고치세요" 와 패치 제안입니다. 프로덕션 저장소에서는 그게 맞지만, 학습 저장소에서는 **학습을 파괴합니다.** 봇이 답을 주면 나는 그걸 붙여넣고, 코드는 좋아지고, 머리에는 아무것도 안 남습니다.

그래서 모든 리뷰어 프롬프트(`.github/review-prompts/`, `.claude/commands/`)에 동일한 규칙을 박아 두었습니다.

> 수정된 코드, 패치, "이렇게 바꾸세요" 를 절대 쓰지 마라. 어긋난 지점을 가리키고 질문만 해라.

봇이 이 규칙을 어기고 코드를 주기 시작하면 프롬프트를 조여야 합니다. 그때가 하네스를 점검할 시점입니다.

## 설계 원칙 둘: 백지 설명이 리뷰의 입력이다

PR 템플릿의 첫 칸이 `## 백지 설명` 입니다. 코드를 보지 않고 이 변경이 무엇을 왜 하는지 산문으로 쓰는 칸입니다.

리뷰 봇의 주 임무는 코드를 보는 것이 아니라 **이 글과 코드의 괴리를 찾는 것** 입니다. 내가 "이런 걸 만들었다" 고 쓴 글과 실제로 만든 것 사이의 틈이, 곧 내가 자각하지 못한 잘못된 모델입니다.

특히 세 번째 유형을 노립니다. **설명이 주장하는 보장을 코드가 실제로는 제공하지 않는 경우.** `acks=all` 이라고 쓰고 실제로는 `acks=1` 인 코드를 짜는 것이 정확히 이 유형이고, 원본 구현이 그렇게 되어 있습니다.

## 4개 층

### 층 0. 기계 게이트 (사람도 AI도 개입 안 함)

`.github/workflows/verify.yml` 이 PR 마다 돕니다.

| 검사 | 하는 일 |
|---|---|
| 학습 절차 게이트 | `.github/scripts/learning_gate.py` |
| 빌드와 단위 테스트 | Maven. `pom.xml` 이 없으면 건너뜀 |
| 시드 스윕 (짧게) | 시뮬레이터 200 시드. `simulation/` 이 없으면 건너뜀 |

학습 절차 게이트가 보는 것은 코드 품질이 아니라 절차입니다.

- `reference/` 가 수정되었는가 (원본은 비교 기준이라 얼면 안 됨)
- 프로덕션 코드가 바뀌었는데 테스트 변경이 없는가 (재현 테스트를 건너뛴 것)
- 프로덕션 코드가 `System.currentTimeMillis`, `Thread.sleep` 등 실제 시계를 직접 부르는가 (ADR 0003 위반, 시뮬레이터가 비결정적이 됨)
- PR 본문에 `## 백지 설명` 이 있고 실제로 채워졌는가
- 긴 대시가 들어갔는가 (AGENTS.md 글쓰기 규칙)

**이 게이트는 우회하지 않습니다.** 바빠지면 사람은 반드시 재현 테스트를 건너뛰고 구현부터 합니다. 그 순간 이 저장소는 코드 옮겨 적기가 됩니다.

### 층 1. 다관점 AI 리뷰 (PR 마다 자동)

서로 다른 계보의 모델을 셋 붙입니다. **같은 모델에게 두 번 물으면 같은 사각지대가 두 번 나오기 때문** 입니다.

| 리뷰어 | 역할 | 실제 비용 | 규칙을 주는 곳 |
|---|---|---|---|
| Claude | 백지 설명과 코드의 괴리, 빠진 개념, 검증 안 된 불변식 | Claude 개인 구독 차감 | `.github/review-prompts/concept-gap.md` |
| Codex | 불변식 공격, 데이터 유실 시나리오 | ChatGPT 개인 구독 차감 | `AGENTS.md` 의 `## Code Review Rules` |
| CodeRabbit | 코드 품질, 실제 버그, 라인별 코멘트 | 공개 저장소 무료 | `.coderabbit.yaml` |

셋 다 계보가 다른 모델입니다. 같은 모델에 두 번 물으면 같은 사각지대가 두 번 나오기 때문에 이게 요점입니다.

역할이 겹치지 않게 나눠 두었습니다. Claude 와 Codex 는 스타일과 네이밍을 아예 보지 말라고 지시해 두었고, 그건 CodeRabbit 이 합니다. 반대로 CodeRabbit 은 개념과 설명의 괴리를 보지 않습니다.

**세 리뷰어 전부에게 같은 제약을 걸었습니다.** 수정안 생성 금지입니다. 각자 규칙을 읽는 위치가 달라서 세 곳에 따로 박아야 했습니다.

- Claude: 워크플로가 `.github/review-prompts/` 의 프롬프트를 주입
- Codex: 공식 문서대로 `AGENTS.md` 의 `## Code Review Rules` 섹션을 읽습니다. `@codex fix` 요청이 와도 수정안을 만들지 말라고 명시해 두었습니다
- CodeRabbit: `.coderabbit.yaml` 의 `tone_instructions` 와 경로별 `path_instructions`

CodeRabbit 의 경로별 지시는 이렇게 나눠 두었습니다.

| 경로 | 무엇을 보게 했는가 |
|---|---|
| `**/*.java` | 데이터 유실과 조용한 손상. 버퍼 크기 계산, 문자 수와 바이트 수 혼동, 길이 필드를 믿고 allocate 하는 것 |
| `simulation/**` | 비결정성의 원천. HashMap 순회 순서, 스레드 스케줄링 의존, 시드 없는 난수 |
| `docs/**/*.md` | 기술적 사실 오류와 논리적 모순만. 문장 다듬기 금지 |
| `.github/**` | 트리거가 의도와 맞는지, 시크릿이 로그로 새지 않는지 |

`reference/` 는 리뷰 대상에서 제외했습니다. 원본 코드에 리뷰가 달리면 노이즈입니다.

### Claude 리뷰를 언제 도는지

`pull_request` 의 `synchronize` 는 **일부러 뺐습니다.** 커밋을 푸시할 때마다 리뷰가 돌면 개인 구독 사용량이 녹습니다. PR 을 처음 열 때와 draft 를 푸는 시점에만 자동으로 돌고, 수정 후 다시 받고 싶으면 PR 에 `/review` 코멘트를 남기면 됩니다.

이 저장소에서는 그게 오히려 맞습니다. 리뷰의 입력이 백지 설명이라, 설명을 고치지 않고 코드만 푸시한 상태에서 리뷰를 또 받을 이유가 없습니다.

### 검토했다가 뺀 것: Gemini Code Assist

처음에는 세 번째 리뷰어로 넣었다가 뺐습니다. 확인해 보니 "설치하면 무료" 가 아니었습니다.

- GitHub 통합은 아직 **Preview** 이고, 문서상 "Preview 동안 과금 없음" 이지만 **유효한 Google Cloud 결제 계정이 필요** 합니다
- 개인 무료 등급의 PR 리뷰 할당량이 명확히 문서화되어 있지 않습니다. 월 8건이라는 이야기가 돌지만 공식 문서에서 숫자를 확인하지 못했습니다
- 저장소 하나 붙이자고 GCP 프로젝트와 결제 계정을 만드는 비용이 얻는 것보다 큽니다

나중에 Preview 가 풀리고 조건이 명확해지면 다시 검토합니다. 세 번째 관점은 Codex 로 채웠습니다. ChatGPT 개인 구독으로 되고, 결제 계정을 새로 만들 필요가 없고, 무엇보다 **다른 계보의 모델** 이라는 원래 목적을 그대로 만족합니다.

### 층 2. 적대적 검증 (요청할 때만)

PR 에 `/adversary` 코멘트를 남기면 적대적 검증자가 붙습니다. 이 역할은 하나만 합니다. **이 코드를 깨뜨리는 구체적인 이벤트 순서를 찾는 것.**

크래시 타이밍, 부분 실패, 재시작 후 복구, 동시성, 경계값, 네트워크 재정렬, 리더 교체를 순서대로 공격합니다.

프롬프트에 정직 규칙을 넣었습니다. 반례를 못 찾으면 못 찾았다고 쓰고, "확실히 깨진다" 와 "깨질 것 같다" 를 구분해서 쓰게 했습니다. 억지 반례는 시간을 낭비시키고, 몇 번 반복되면 리뷰를 안 읽게 만듭니다.

### 층 3. 로컬 슬래시 커맨드

PR 을 올리기 전에 쓰는 것들입니다. `.claude/commands/` 에 있습니다.

| 커맨드 | 쓰는 시점 | 하는 일 |
|---|---|---|
| `/design-review` | 구현 **전** | 설계의 암묵적 가정을 꺼내서 질문. 코드를 절대 안 씀 |
| `/adversary` | 구현 **직후** | 반례를 찾고 실패하는 테스트까지 작성. 고치지는 않음 |
| `/explain-check` | 사이클 끝 | 백지 설명을 받아 코드와 대조, 설명 가능한 상태인지 판정 |
| `/kafka-diff` | 사이클 끝 | 실제 Kafka 소스와 KIP 을 찾아 대조 |
| `/second-opinion` | 확신이 안 설 때 | 같은 질문을 Codex 에 던져 교차 검증 |

`/design-review` 가 특히 중요합니다. 구현 전에 쓰면 설계 결함을 코드 쓰기 전에 잡고, 무엇보다 **내가 답할 수 없는 질문이 어디인지** 가 드러납니다. 즉답할 수 있는 질문만 나왔다면 그 리뷰는 가치가 없었던 것입니다.

### 층 4. 커리큘럼 자체에 대한 리뷰 (주 1회)

`.github/workflows/curriculum-review.yml` 이 매주 월요일에 이슈 목록과 ADR 전체를 읽고 이슈 하나를 만듭니다. 코드가 아니라 **학습 계획** 을 봅니다.

- Kafka 를 백지에서 설명하려면 알아야 하는데 커리큘럼 어디에도 없는 개념
- 순서 오류
- 한 줄로 적혀 있는데 사실 가장 배울 게 많은 항목
- 완료 조건이 "구현했다" 로만 되어 있고 "이해했다" 를 확인 못 하는 이슈

항목을 추가하자고 할 때는 무엇을 뺄지도 같이 말하도록 프롬프트에 박았습니다. 안 그러면 커리큘럼이 무한히 부풀어 오릅니다.

### 야간 시드 스윕

`.github/workflows/nightly-sweep.yml` 이 매일 새벽 3시(KST)에 시뮬레이터를 2만 시드 돌립니다. 불변식 위반이 나오면 자동으로 이슈를 만듭니다.

PR 게이트에서 200 시드만 도는 이유는 속도입니다. 진짜 희귀한 타이밍 버그는 야간에 잡습니다.

## 직접 해야 하는 설정

워크플로 파일은 이미 들어가 있습니다. 다음은 저장소 소유자만 할 수 있어서 남겨둡니다.

### 1. Claude 리뷰 인증: 개인 구독으로 됩니다

API 키가 필요 없습니다. Pro 또는 Max 구독이 있으면 로컬에서 장기 토큰을 발급해 그걸 저장소 시크릿에 넣으면 됩니다.

```bash
claude setup-token
# 브라우저 인증이 끝나면 토큰이 출력됩니다. 그 값을 아래에 붙여넣습니다.

gh secret set CLAUDE_CODE_OAUTH_TOKEN -R PreAgile/kafka-from-scratch
```

알아둘 것 세 가지입니다.

- **사용량은 개인 구독에서 차감됩니다.** 별도 과금은 없지만 내가 로컬에서 쓸 몫을 나눠 쓰는 것입니다. 그래서 `synchronize` 트리거를 뺐습니다
- **토큰은 만료됩니다.** 리뷰 잡이 인증 오류로 실패하기 시작하면 `claude setup-token` 을 다시 돌려 시크릿을 갱신하세요
- **인라인 코멘트 분류 기능은 OAuth 로 못 씁니다.** 그 기능만 `anthropic_api_key` 를 요구합니다. 이 하네스는 PR 본문 코멘트로 리뷰를 남기므로 영향이 없습니다

시크릿이 없으면 AI 리뷰 잡은 **조용히 건너뜁니다.** 층 0 의 기계 게이트는 그대로 돕니다.

### 2. Codex 리뷰 켜기

워크플로 파일이 아니라 설정 페이지에서 켭니다. GitHub Actions 를 쓰지 않으므로 시크릿도 필요 없습니다.

1. https://chatgpt.com/codex/settings/code-review 로 갑니다
2. `PreAgile/kafka-from-scratch` 에 Code review 를 켭니다 (저장소 push 또는 admin 권한 필요)
3. 자동 리뷰를 원하면 Automatic reviews 를 켭니다. 끄면 PR 에 `@codex review` 로 요청할 때만 돕니다

트리거는 세 가지입니다.

| 코멘트 | 하는 일 |
|---|---|
| `@codex review` | 일반 리뷰 |
| `@codex security review` | 보안 중심 (research preview) |
| `@codex fix ...` | **쓰지 마십시오.** `AGENTS.md` 에서 수정안 생성을 금지했지만 애초에 요청하지 않는 게 맞습니다 |

리뷰 규칙은 저장소의 `AGENTS.md` 의 `## Code Review Rules` 섹션에서 읽습니다. 루트 `AGENTS.md` 와 변경된 파일에 가장 가까운 `AGENTS.md` 를 함께 적용합니다. 나중에 `log-engine/AGENTS.md` 같은 하위 파일을 두면 그 디렉터리에만 적용되는 규칙을 더할 수 있습니다.

ChatGPT 개인 구독 사용량에서 차감됩니다. Claude 와 마찬가지로, 리뷰를 여러 번 받을수록 로컬에서 쓸 몫이 줄어듭니다.

### 3. CodeRabbit

이미 설치되어 있습니다. PR #25 에서 자동으로 붙어 코멘트를 남기는 것을 확인했습니다.

공개 저장소는 신청이나 승인 대기 없이 Pro 기능이 무료로 켜집니다. 신용카드도 필요 없습니다. 속도 제한은 시간당 200파일, 연속 3회 리뷰 후 시간당 4회입니다. PR 을 연달아 여러 개 올리면 "Review rate limited" 가 뜨는데, 혼자 작업에서는 평소 닿지 않는 수준입니다.

설정은 `.coderabbit.yaml` 에 들어 있어서 따로 할 일은 없습니다.

### 4. 브랜치 보호

```bash
gh api -X PUT repos/PreAgile/kafka-from-scratch/branches/main/protection \
  --input .github/branch-protection.json
```

`main` 직접 푸시를 막고 PR 을 강제합니다. 혼자 하는 프로젝트라 과해 보이지만, **PR 을 통과해야 리뷰가 붙습니다.** 직접 푸시하면 이 하네스 전체가 무용지물이 됩니다.

## 한 사이클에서 하네스가 어떻게 끼어드는가

```
1. 이슈를 고른다
2. /design-review      로컬. 구현 전 설계 검토
3. 재현 테스트를 쓴다   실패하는 것을 눈으로 확인
4. 구현한다             직접. 에이전트에게 코드를 받지 않는다
5. /adversary          로컬. 반례 사냥
6. PR 을 올린다         백지 설명을 채운다
     → 층 0 기계 게이트
     → 층 1 Claude(개념 갭) + Codex(불변식 공격) + CodeRabbit(코드 품질)
7. /adversary 코멘트    필요하면 PR 에서 한 번 더
8. /explain-check      로컬. 설명 가능한 상태인지 판정
9. /kafka-diff         실제 Kafka 와 대조, docs/notes/ 에 기록
10. 머지
```

2번과 8번이 이 하네스의 핵심입니다. 나머지는 거들 뿐입니다. 구현 전에 내가 모르는 것을 드러내고, 구현 후에 내가 안다고 착각하는 것을 드러냅니다.

## 겪은 함정: 허용 목록으로 리뷰어를 묶으면 코멘트를 못 남긴다

처음에 Claude 리뷰 잡에 `--allowedTools` 로 읽기 도구만 허용했습니다. 리뷰어가 파일을 고치지 못하게 하려는 의도였습니다.

결과는 이랬습니다. 잡은 3분 반을 돌고 `success` 로 끝났는데 **PR 에 아무것도 남지 않았습니다.** 로그를 보니 `permission_denials_count: 9` 였습니다. 액션이 코멘트를 게시하는 데 쓰는 자기 도구까지 허용 목록에서 빠져서 전부 거부된 것입니다. 워크플로는 성공으로 표시되고 리뷰만 사라지는, 가장 알아채기 어려운 실패였습니다.

허용 목록을 거부 목록으로 바꿨습니다.

```yaml
claude_args: |
  --disallowedTools "Edit,Write,MultiEdit,NotebookEdit"
```

이쪽이 의도에도 더 맞습니다. 막고 싶은 것은 "읽기 외의 모든 것" 이 아니라 **파일 수정** 이었습니다. 이제 리뷰어는 코드를 물리적으로 고칠 수 없고, 코멘트는 남길 수 있습니다. ADR 0004 의 수정안 금지 원칙이 프롬프트뿐 아니라 도구 수준에서도 강제됩니다.

교훈은 일반적입니다. **워크플로가 success 인데 산출물이 없으면 권한 거부를 먼저 의심하십시오.** 거부는 잡을 실패시키지 않습니다.

## 겪은 함정 둘: 코멘트로 트리거되는 워크플로는 기본 브랜치 것이 돈다

위 문제를 고쳐 브랜치에 푸시하고, 그 PR 에 `/review` 코멘트를 남겨 재검증했습니다. 그런데 거부가 계속 났습니다.

원인은 이랬습니다. `issue_comment` 이벤트로 트리거되는 워크플로는 **항상 기본 브랜치(main)의 워크플로 파일을 실행합니다.** PR 브랜치에 아무리 고쳐 넣어도 코멘트 트리거는 그 수정을 보지 못합니다. 실행 기록에도 `branch=main` 으로 찍힙니다.

이건 GitHub 의 의도된 동작이고 보안상 그래야 합니다. 그렇지 않으면 외부인이 PR 을 열어 워크플로를 고친 뒤 코멘트 하나로 그걸 실행시킬 수 있습니다.

실무적인 결론은 이렇습니다.

| 트리거 | 어느 브랜치의 워크플로가 도는가 | 검증 방법 |
|---|---|---|
| `pull_request` | PR 브랜치 | PR 브랜치에서 바로 확인 가능 |
| `issue_comment`, `schedule`, `workflow_dispatch` | 항상 기본 브랜치 | **main 에 머지한 뒤에만 검증 가능** |

`/review`, `/adversary`, 야간 스윕, 주간 커리큘럼 검토는 전부 두 번째 부류입니다. 이들의 워크플로를 고쳤다면 main 에 들어간 다음에야 실제 동작을 확인할 수 있습니다. 브랜치에서 아무리 돌려봐도 구버전이 돕니다.

## 겪은 함정 셋: track_progress 는 워크플로가 기본 브랜치와 같아야 돈다

`track_progress: true` 를 넣고 다시 돌렸더니 이번엔 잡이 5초 만에 끝났습니다. Claude 가 아예 실행되지 않았습니다. 로그에 이유가 그대로 있었습니다.

```
Auto-detected mode: tag for event: pull_request
Skipping action due to workflow validation: Workflow validation failed.
The workflow file must exist and have identical content to the version on
the repository's default branch.
...
your workflow will begin working once you merge your PR.
```

`track_progress` 를 켜면 액션이 **워크플로 파일이 기본 브랜치의 것과 바이트 단위로 같은지** 검사합니다. PR 에서 워크플로를 고치면 그 PR 에서는 액션이 스스로 건너뜁니다.

이것도 의도된 보안 동작입니다. 이 모드에서 액션은 앱 토큰을 받아 PR 에 코멘트를 쓸 권한을 얻습니다. 워크플로를 고친 PR 에서 그대로 실행된다면, 외부인이 워크플로를 바꿔 그 권한을 탈취할 수 있습니다.

### 세 함정이 만든 사슬

세 개가 순서대로 겹쳐서 진단이 길어졌습니다.

| 순서 | 증상 | 원인 | 로그의 단서 |
|---|---|---|---|
| 1 | success 인데 코멘트 없음 | `--allowedTools` 허용 목록이 코멘트 게시 도구를 제외 | `permission_denials_count: 9` |
| 2 | 거부 목록으로 바꿔도 여전히 없음 | `track_progress` 가 꺼져서 코멘트용 MCP 도구가 애초에 없음 | SDK 옵션에 `mcpServers` 부재 |
| 3 | `track_progress` 를 켜니 5초 만에 종료 | 워크플로를 고친 PR 이라 액션이 자체 검증에서 스킵 | `Workflow validation failed` |

공통점이 하나 있습니다. **세 번 다 워크플로는 `success` 였습니다.** 권한 거부도, 자체 스킵도 잡을 실패시키지 않습니다.

### 그래서 지켜야 하는 검증 순서

리뷰 워크플로를 수정했다면 이 순서 말고는 검증할 방법이 없습니다.

1. 워크플로 수정을 PR 로 올린다. **그 PR 에서는 리뷰가 안 돈다.** 정상이다
2. main 에 머지한다
3. **워크플로를 건드리지 않는** 별도의 PR 을 열어서 확인한다

2번을 건너뛰고 브랜치에서 아무리 돌려봐도 영원히 안 됩니다. 함정 둘(코멘트 트리거는 기본 브랜치 것이 돈다)과 합치면, 리뷰 하네스는 **main 에 들어간 뒤에만 검증 가능** 하다는 결론이 됩니다.

### 판별법

워크플로가 `success` 인데 리뷰가 없을 때 로그에서 이 순서로 찾으십시오.

1. `Workflow validation failed` 가 있으면 함정 셋. 머지하면 됩니다
2. `permission_denials_count` 가 0 이 아니면 도구 권한 문제
3. `SDK options` 에 `mcpServers` 가 없으면 `track_progress` 문제
4. 셋 다 아니면 그때 프롬프트를 의심하십시오

## 첫 리뷰가 실제로 잡은 것

세 함정을 통과한 뒤 PR #28 에서 개념 갭 리뷰가 처음 돌았습니다. 1분 53초, 15턴이었습니다. 결과가 하네스의 설계 의도를 그대로 증명했습니다.

**설계대로 동작한 부분**

- 수정안을 한 줄도 쓰지 않았습니다. 위치를 가리키고 질문만 했습니다
- 한국어 존댓말, 긴 대시 없음
- 지적할 것이 없는 절(검증되지 않은 불변식)에는 "해당 없음" 이라고만 썼습니다. 억지로 채우지 않았습니다

**실제로 잡은 것**

가장 중요한 지적은 이것입니다. 0주차 노트에 "Kafka 가 기본적으로 fsync 를 하지 않기로 했다" 고 썼는데, `ADR 0001` 은 상태가 초안이고 결정 내용은 "배치화하되 완전히 끄는 것을 기본값으로 삼지 않는다" 였습니다. **실제 Kafka 의 선택과 이 프로젝트가 앞으로 내릴 결정을 한 문장 안에서 구분 없이 섞어 쓴 것** 입니다.

이게 정확히 이 하네스를 만든 이유입니다. 글을 쓴 사람은 머릿속에서 둘을 구분하고 있다고 믿지만, 문장에는 구분이 없습니다. 그 상태로 몇 주가 지나면 "내가 왜 이렇게 결정했지" 를 복원할 수 없습니다.

나머지 두 지적도 유효했습니다. 인과 사슬이 acks 에서 끝나는데 `min.insync.replicas` 가 빠져 있고, 같은 전제에서 나오는 리더 에포크가 사슬 안에 들어가는지 별개인지 언급이 없다는 것이었습니다. 세 번째는 파일명이 `docs/notes/README.md` 가 정한 규칙과 다르다는 지적이었습니다.

세 가지 다 반영했습니다. 특히 두 번째를 반영하면서 사슬이 한 번 갈라진다는 것을 알게 됐습니다. ISR 과 HW 가 다루는 문제(얼마나 복제됐나)와 에포크가 다루는 문제(어느 로그가 진짜인가)는 같은 전제에서 나오지만 축이 다릅니다. 리뷰를 받기 전에는 그냥 사슬 하나로 알고 있었습니다.

**한 번의 리뷰로 제 글의 사실 오류 하나와 개념 공백 둘이 나왔습니다.** 코드가 아직 한 줄도 없는 상태에서 나온 결과입니다.

## 이 하네스의 한계

정직하게 적어둡니다.

- **AI 리뷰는 틀립니다.** 특히 분산 시스템의 타이밍 문제에서 그럴듯하지만 실제로는 일어날 수 없는 시나리오를 잘 만듭니다. 그래서 `/adversary` 는 반례를 **테스트로 재현해서 실패를 확인** 하게 했습니다. 재현 안 되는 반례는 버립니다.
- **셋이 같은 것을 지적하면 신호가 아니라 노이즈일 수 있습니다.** 비슷한 데이터를 봤기 때문입니다. 진짜 신호는 한쪽만 지적한 것 중에 재현되는 것입니다. Claude 와 Codex 의 판단이 갈리는 지점이 특히 볼 만합니다.
- **구독 사용량이 두 군데서 빠집니다.** Claude 리뷰는 Claude 구독, Codex 리뷰는 ChatGPT 구독에서 차감됩니다. 리뷰를 습관적으로 여러 번 돌리면 정작 구현할 때 쓸 몫이 줄어듭니다. 자동 트리거를 최소로 둔 이유입니다.
- **게이트를 우회하고 싶어지는 순간이 옵니다.** 그때가 이 프로젝트가 실패하는 지점입니다. 게이트를 고치지 말고 절차를 지키거나, 절차가 정말 틀렸다면 ADR 을 쓰고 고치세요.
